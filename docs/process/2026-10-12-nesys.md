# NESYS service — 2026-10-12

Target stays TG4AC 5.80.02, IDA instance `ida-47892`, image base `0x140000000`.
The module is `dll/src/features/nesys`. `[Nesys] Enabled=0` installs nothing.

## Why nothing reached the server

The game does not speak HTTP. Every content command and the card calls go
through the NESYS client library linked into the exe, which talks to the
cabinet's NESYS service over the message pipe `\\.\pipe\nesys_games`
(`sub_140005260`, `sub_140008840`). Without that pipe `NESYS_INIT`
(`sub_140001000`) fails and `Code` stays null, so:

- `NesysManager_IsConnected` (`sub_140228680`) is false. It needs manager
  `+4` (init ok), `Code+8300`, `+5` (network up), and `+6` clear. The NESiCA
  mode button stays grey.
- `NESYS_CARD_SELECT` (`sub_140002930`) returns -1.
- `NESYS_HTTPACCESS_POST` (`sub_140001FB0`) returns -1 for ping
  (`sub_14023F520`) and for every command (`sub_140241B20`).
- `NesysManager_IsAbleSend` (`sub_140228610`) also needs `+9`, which only a
  successful ping sets (`sub_140239800`).

The old menu-flag writes in `card.cpp` could not fix this and were removed.

## Pipe protocol

Message pipe, one message per write: `[u32 command][u32 length][payload]`.
The client reads with a 4 KB buffer and joins `ERROR_MORE_DATA` chunks.
Replies are mapped to callback events by `sub_140005F40` and handled by
`sub_140215D40`.

| Game sends | Service replies | Effect in the game |
| --- | --- | --- |
| `0x01` CLIENT_START (pid, exe path, `2.81(x64) 2015/03/24`) | `0x10D` | event 25, sends SET_INCOME_MODE |
| `0x02` CONNECT | `0x10E`, `0x103`, `0x107` | `0x103` is event 6: `+5 = 1`. `0x107` is event 1: `+6 = 0`, `Code+8300 = 1`, host setup |
| `0x09` CARD_SELECT | `0x111` | event 7, `sub_140217600` parses the card data as JSON |
| `0x0A` / `0x0B` CARD_INSERT / UPDATE | `0x112` / `0x113` | events 8 / 9 |
| `0x1B` HTTPACCESS_POST | `0x121`, `0x122` | event 35, `sub_140239800` |
| `0x14` LOCALNW_INFO | `0x11B`, `0x11C` | events 27, 16 |
| `0x15` GLOBALADDR | `0x11D` | event 17 |
| `0x18` SERVICE_VERSION | `0x120` | event 14 |
| `0x20` SET_INCOME_MODE | `0x125` | event 39 |

`0x103` has to come before `0x107`: event 1 runs the server-profile setup
(`sub_140228CF0`) only while `+5` is set. `DISCONNECT_REPLY` (`0x10F`) is sent
only when the game asks, because its event clears `+5`.

### CERT_INIT_NOTICE (`0x107`)

| Offset | Field |
| --- | --- |
| 0 | tenpo table, 120 bytes: id, name[31] at 4, address[33] at 35, ticket[33] at 68, prefecture[17] at 101 |
| 120 | news table, 1032 bytes (type, size, path[1024]) |
| 1152 | server profile length |
| 1156 | server profile text |

The profile is `game`. `sub_140228CF0` matches it against its table and the
content hook then rewrites both hosts to `127.0.0.1:<port>/ahac-api/tg4gs/gs`.

### HTTPACCESS_POST (`0x1B`) and its reply (`0x122`)

Request, built by `sub_140001FB0`: URL[1025] at 0, proxy[1025] at 1025, auth
name[33] at 2050, password[33] at 2083, port at 2116, sequence at 2120,
timeout at 2124, mode at 2128, data size at 2132, header[1025] at 2136, data
at 3161. The game sends port 80 and a full URL with the host, so the URL wins.

Reply: header text[1028] at 0, HTTP status at 1028, error at 1032, sequence at
1036, body size at 1040, body at 1044. A non-zero error or a 3xx–5xx status is
an error. Otherwise the first body line must be `1` (`_wtoi`) and the rest is
UTF-8 JSON (`sub_140218CC0`). Every unit on the login vtable returns true from
slot `+536` (`sub_140197C00`, "has a result line") and false from `+544`.

The content server now writes `1\n` before every API response.

### Card calls

CARD_SELECT payload: id[16], data type at 16 (the game sends 4), parameter
size at 20, parameter text at 24. CARD_INSERT / UPDATE / BUYS_ITEM: id[16],
frequency at 16, transfer mode at 20, data type at 24, data size at 28, data
at 32. The card reply is `[status][times][days][size][data]`; status 1 is
success and the data is the JSON the game parses directly (no result line).

| Command | Content route |
| --- | --- |
| CARD_SELECT | `selectcard` |
| CARD_INSERT | `registercard` |
| CARD_UPDATE | by data type, see the fifth pass |
| CARD_BUYS_ITEM, TAKEOVER, DECREASE, REISSUE_TEST, PLAYED_LIST | `cardbuysitem`, `cardtakeover`, `carddecrease`, `cardreissuetest`, `cardplayedlist` |
| CARD_REISSUE | `reissuecard` |

The body is the game's document with `card_id` added (or `{"card_id", "param"}`
for a text parameter). The server resolves `player_id` from `card_id` when the
request carries no player.

HTTPS requests (`0x26`, `0x27`) were first left unanswered; since the fourth
pass they are answered like HTTP (see below).

## Card reader

> Superseded on 2026-10-13 (fourth pass below): the export stubs and the IsCan
> replacement were removed.

`card.cpp` now fills the null reader export slots at DLL load instead of
hooking the poll and GetID. `StartReadNESiCA` (`sub_140244E80`) calls
`NESiCAReaderRead`; `GetResult` returns 4 until the card key taps, then 0.
`StopReadNESiCA` (`sub_140245AC0`) calls `NESiCAReaderCancelRead`.

The device-error byte `+180` that the missing USB IO sets is left alone.
`MarshallingIO.IsError` (`sub_1402273D0`) returns it, and the blueprints use
it to drive the train from the keyboard. The earlier card code cleared it
every frame, so the game read the empty cabinet image instead: the horn
(active-low) sounded nonstop and no control answered. `MarshallingIO.IsCan`
(`sub_140227350`, called only from its exec thunk) is replaced to return
`+108 && reader+25`, so NESiCA is available while `+180` stays set.

## Operator setting that gates NESYS (2026-10-12, second pass)

The first run with the service showed no pipe client at all. The game starts
NESYS only from blueprints, through `NesysManager_Update` (`sub_1402FCD20` ->
`sub_140228C40` -> `sub_140246240`, which calls `NESYS_INIT` once), and only
while `MyGameInstance_C.IsUsedNesys` is true. That reads the operator setting
`HardSaveGame_C.IsNesysUsed` (`MyGameInstance_C.HardSave`). No HardSave slot
exists, so the default (off) applied. `IsUsedNESiCATime` additionally limits
NESiCA to the `NESiCATime_<weekday>` windows.

`operator_settings.cpp` sets `IsNesysUsed = true` and `IsUsedNESiCATime =
false` on every `HardSaveGame_C` object, the class default included: when
`UGameplayStatics::CreateSaveGameObject` (`sub_1412C2440`) or
`LoadGameFromSlot` (`sub_1412D0600`) returns one, and on a 200 ms rescan of
`GUObjectArray` so a later blueprint write does not stick. The fields are
found by reflection. UE 4.15 here keeps `UProperty::Offset_Internal` at
`+0x50` (constructor `sub_1405DD5B0` stores it there) and the
`UBoolProperty` masks at `+0x79..+0x7B`. The earlier menu-flag code read the
offset at `+0x44`, which is why every write was rejected.

The next run resolved the fields (`IsNesysUsed` at `+0x414`,
`IsUsedNESiCATime` at `+0x3A1`) and found nothing to change: both were
already as wanted. Still no pipe client. `NesysManager_Update` is referenced
only by `MyGameInstance.uasset` and was never called (wrong, see the fourth
pass: the update driver was removed). `update_driver.cpp`
hooks `sub_140228C40` (the update, `float DeltaSeconds`) to see blueprint
calls, and `UMarshallingIO::Update` (`sub_1402467A0`, every frame on the game
thread, menus included) as the clock: after a second without a blueprint
update it calls the original update with the measured frame time. The first
call runs `NESYS_INIT`; its result is logged from a hook on `sub_140001000`.
`NesysManager_Create` (`sub_140227FC0`) only creates the singleton when it is
missing, so a later blueprint call does not reset it.

The run after that showed the blueprints do call the update every frame, and
`NESYS_INIT` still never ran. The NesysManager constructor (`sub_14020BE90`)
stores state 2 (disabled) when `WholeGameConfig.DisableNESYS` (class default
`+0x58`, `Config/DefaultGame.ini` has `DisableNESYS=True`) is set or the
environment has `AH_NESYS_DISABLE`; `sub_140246240` only initializes from
state 0. The same ini section has `UseKeyboardDevice=True` and
`UseKeyboardDeviceWithCardReader=False`, which leaves the card reader out of
the keyboard setup. Layout of the class default (checked against
`WindowTopmost` at `+0x94`, read by `sub_140205E70`): `DisableNESYS` `+0x58`,
`SplitScreens` `+0x5C`, `SaveGamePath` `+0x60`, `UseKeyboardDevice` `+0x90`,
`UseKeyboardDeviceWithCardReader` `+0x91`.

`operator_settings.cpp` now hooks the constructor and turns state 2 into 0,
and its settings table also writes `DisableNESYS = false` and
`UseKeyboardDeviceWithCardReader = true` on the `WholeGameConfig` class
default, logging the value it replaced. The game files are not edited.

## I/O error screen and keyboard NESiCA (third pass)

With `NESYS_INIT` running the pipe connected, but two things went wrong:

- Forcing `UseKeyboardDeviceWithCardReader = true` made the keyboard setup
  check the cabinet USB-I/O, which is absent, and the game stopped on
  入出力装置エラー (it also sent DISCONNECT). That override was removed; the ini
  value (False) stands.
- The first ping went to `http://game.ahac.nesica.net/ahac-api/tg4gs/gs/ping`.
  On the first connection event 1 takes the `+7` branch (`sub_1402211D0`), not
  `sub_140228CF0`, so the content host hook never ran. The hook was removed
  and the NESYS service now rewrites any URL whose path starts with
  `/ahac-api/tg4gs/gs` to `127.0.0.1:<port>` with the same path. Other URLs
  are refused and logged.

In the keyboard setup NESiCA goes through `KeyboardInput`, a developer path:
`StartReadNESiCA` (`loc_140206DD0`) sets `+48`, `StopReadNESiCA`
(`sub_140206F30`) clears `+48/+49`, `GetNESiCAReadState` (`sub_1401EFAF0`)
returns 4 idle, 1 reading, 2 once `+49` is set, `GetNESiCAID`
(`sub_1401EF9D0`) returns the FString at `+296`, and `SetMimicNESiCAID`
(`sub_140205550`) copies an id there (FString copy, `sub_1401994A0`) and sets
`+49`. `card.cpp` hooks the read state: while `+48` is set and no card is
present, a fresh key tap calls `SetMimicNESiCAID` with the configured id.

## Fourth pass (2026-10-13): input device, NESiCA play flag, trace

Blueprints were read with UAssetGUI (`tojson ... VER_UE4_15`) and a small
Kismet printer; offsets below are bytecode offsets in those dumps.

### Driving locked, horn nonstop

`MyGameInstance` picks the device per call. `MasterController` returns
`marshallingIO.MasterController` while `IsCan && !UseKeyboardDeviceWithCardReader`
and `keyboardIO.MasterController` otherwise; `HornButtonAtKeyboard` and the
other `*AtKeyboard` functions forward keyboard input only while `!IsCan`.
The IsCan replacement made IsCan true, so the train read the empty cabinet
image (horn active-low) and ignored the keyboard — the same failure as the
earlier `+180` clearing. IsCan is no longer touched.

The cabinet reader path was dead anyway: `MarshallingIO.StartReadNESiCA`
(`sub_140244E80`) needs reader `+24`, which only a loaded `ArrowheadUSBIO.dll`
sets. That is why P never produced a card log. The export stubs were removed.

### Reading a card

`MyGameInstance.StartReadNESiCA` / `NESiCAReadState` / `GetNESiCAID`: outside
test mode they need `NesysManager_IsAbleSend && HardSave.InnerNESiCATime`
(`StartReadNESiCA` also `!IsFestivalMode`), then use MarshallingIO when IsCan,
KeyboardInput otherwise. `InnerNESiCATime` is set every frame by
`HardSaveGameProcess.UpdateNESiCATime` when `IsUsedNESiCATime` is off.
`ENESiCAReadState`: 0 Idle, 1 Reading, 2 Success, 3 Error, 4 NoRead.

`MainMenu_Touch.onNesys` starts the read on sequence 3 (mode select) while
`!NesysManager_IsUsedNESiCA`. `MissionSelectLevel` polls `NESiCAReadState`
every tick until a read finishes: Success runs `ReadNESiCAProcess`, which
reads the id (`NESiCAReadSuccess` -> `NesysManager_SetCurrentCardId`) and
sends `Http_SelectCard` (CARD_SELECT).

### The NESiCA mode button

`typeSelectWidget.ableNESiCA` (hides `NesicaButton_off`, sets `isNesica`) is
called by `MainMenu_Touch` only while `NesysManager_IsUsedNESiCA` is true, and
the main menu logs the player in only then. That flag is `NesysManager+684`;
only `NesysManager_SetUsedNESiCA` (`sub_140228B90`) sets it and only
`TestData/.../DebugResultBaseScreen` calls that. `ResetParameter`
(`sub_14023AFD0`) clears it with the card id (`+664`, default
`7020392000000000`) and player id (`+680`). The service now sets `+684` when a
CARD_SELECT or CARD_INSERT succeeds, before it sends the reply.

### Disconnect after the first connect

CERT_INIT event 1 with `+7` set (first connection) runs `sub_1402211D0`, which
calls NESYS_DISCONNECT. `DISCONNECT_REPLY` (`0x10F`) maps to event 21, which
clears `+5` and `+9`; the game reconnects and the next ping sets `+9` again.

### Update driver removed

`UpdateGameInstance` calls `marshallingIO.Update`, `keyboardIO.Update`,
`NesysManager_Update` and `HardSave.Update` in one sequence every frame. The
driver's "blueprints do not update NESYS" line was a single frame longer than
a second (a load hitch), not missing updates. `state_watch.cpp` keeps the
NESYS_INIT result log and logs the manager flags (`+0`, `+4`, `+5`, `+6`,
Code `+8300`, `+9`, `+684`, `+680`) whenever they change.

### HTTPS and the trace

HTTPSACCESS_GET (`sub_140001D30`): URL at 0, proxy at 1025, user at 2050,
password at 2083, client certificate path at 2116, port at 3142, proxy port at
3144, sequence at 3148, timeout at 3152, mode at 3156 (3160 bytes).
HTTPSACCESS_POST (`sub_140002270`) adds data size at 3160, header at 3164 and
the data at 4189. Both are answered with HTTPACCESS_START/REPLY like HTTP: the
game API is forwarded, other hosts (one run asked
`https://cert.nesys.jp/update/cgi/...`) get error 5 as an offline cabinet
would.

`[Nesys] Trace=1` logs every message both ways with a hex head, and HTTP and
card bodies.

Verified with the pipe harness: trace lines, an HTTPS GET to cert.nesys.jp
answered with error 5, an HTTPS ping served with 200, and CARD_SELECT marking
the play before its reply. The game itself was not run.

## Fifth pass (2026-10-13): game API by data type, missions, shop, unlock

### Every game command is a CARD_UPDATE

The trace showed the game sending its API as CARD_UPDATE (and rankings as
RANKING_DATA), not HTTP. Each accessor class names its command (vtable +576)
and its CardUpdateType (vtable +584); `sub_14023F0F0` sends
`NESYS_CARD_UPDATE(raw, accessor->CardUpdateType(), postdata, datasize)`, and
the data type at payload offset 24 is that type. Only accessors with type 0
(`gamemissionresult`, `getpicture`, `getpicturelist`, `postpicture`) use HTTP.
The service used to send every CARD_UPDATE to `playerdata`, so the shop,
item and mission initialisation got player data back.

| Type | Command | Type | Command |
| --- | --- | --- | --- |
| 20 | init | 30 | getmissionranking |
| 21 | mission | 31 | getstoremileageranking |
| 22 | login | 40 | machine unlock (empty name; routed as `machineunlock`) |
| 23 | playend | 50 | shopinitialize |
| 24 | addcredit | 51 | purchaseshopitem |
| 25 | config | 52 | playerbadge |
| 26 | purchasepoint | 53 | playerwappen |
| 27 | gamestart | 55 | iteminitialize |
| 28 | gameresult | 60 | discontinuation |
| 29 | gametotalresult | | |

RANKING_DATA (`0x13`): type, mode, data size at 8, JSON at 12; the reply is
`[status][size][json]` (event 15, `sub_140239270`). Type 31 is the store
mileage ranking; type 10 has no command and is answered as failed. A content
result line `0` (no data) is answered with card status 0.

### Lines empty after NESYS came up

`UHttp_SetupInformation` chains machine unlock, init, rankings, `mission` for
train lines 1–8, `iteminitialize` (categories 11–13) and `shopinitialize`;
`StateCompleted` (`sub_140245300`) advances whatever the result.
`MyGameInstance.MissionDataSettings` applies the mission response with
`ApplyMissionData` (`sub_1401C6C60`) when it is not an error, which also
replaces the mission object's lists — an empty answer left every line without
a mission. The main menu's `Http_SetupMissionData` does the same and goes on
when it fails. The content server has no mission catalog, so it answers
`mission` with result 0 and the game keeps the missions built into it.

### Released missions and the shop

Login (`sub_140211750`) reads `playable_mission`: one array per released
mission and difficulty, `ReleaseMissionData` order — mission number,
difficulty + 1 (`EDifficultyType` Easy, Normal, Hard, Professional), play
count, clear count, rank + 1 (`EScoreRankType` D..SS), total score, near
stop, perfect stop, perfect double — and `playable_realmode` (mission
numbers). `NativePlayerDataObject.GetPlayableMission(mission, difficulty)`
gates every mission on that table. With `[Content] UnlockAll=1` the server
releases all 368 non-debug missions of `MissionData` in all four difficulties
and real mode, and keeps meister points at 99999 or more.

The shop currency is `meister_point` (the purchase reply, `sub_140213690`).
`shopinitialize` (`sub_140233350`) reads `badge`, `wappen` and
`mission_ticket` objects keyed by lineup id with `id`, `price`, `status`,
`buyable`. The server lists every badge and wappen of the game's tables;
`iteminitialize` answers empty lists because `ApplyWappenData`
(`sub_1402000F0`) merges entries over the game's own tables, names included.
The ids come from `server/src/game_catalog.h`, generated by
`server/tools/extract_catalog.py` from UAssetGUI exports of the tables.

Verified with the pipe harness against `ddgac-content`; the game was not run.
