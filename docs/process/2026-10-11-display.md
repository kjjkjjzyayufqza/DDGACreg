## Startup (`Display_Install`)

Same order as upstream `DllMain`:

1. Log to `moduleDir + L"DDGACreg.log"` (upstream used `DDGUltrawide.log`).
2. Load `System32\version.dll` and fill `g_origFuncs` for the thunks.
3. Load `moduleDir + L"config.ini"` (upstream used `DDGUltrawide.ini`). The parser
   only reads `[Output]`, `[Layout]`, `[Source]`, `[TouchPanelWindow]`, `[Touch]`,
   `[Hotkeys]`, and `[Game]`. `[Input]`, `[LayoutMode]`, `[FreeCamera]`, and
   `[Content]` are ignored.
4. `MH_Initialize`. `MH_ERROR_ALREADY_INITIALIZED` is ignored so a later feature
   install can initialize MinHook first. Any other failure skips hooks.
   `InstallGameWindowHook` (when render size is set) and `InstallCommandLineHook`
   run immediately. `ResolveOutput`, `InstallCompositor`, and `InstallTouchHooks`
   run on a worker thread.

Command-line rewriting still forces `-ResX=3840 -ResY=2160 -windowed -ForceRes`
when `[Game]` asks for that size. Compositing, cabinet shaders, and touch
forwarding (`GetCursorPos`, `WindowFromPoint`, `SetCursorPos`, wheel) are unchanged
when the arcade layout is in use.

## Shaders

`dll/CMakeLists.txt` calls `shaders/compile.cmd` with the Windows SDK `fxc.exe`.
That script compiles the same entry points as upstream (`vs_4_0` / `ps_4_0`,
`/O1`, `/Vn g_<file>_<entry>`, `/Fh` bytecode headers). `compositor.cpp` and
`cabinetlight.cpp` include those headers. Nothing is compiled at runtime.

## How `Layout_Query` is consulted

`Layout_Query` is declared in `dll/src/features/layout/layout_api.h` and implemented
by the layout feature. Display does not implement it.

`Placements` builds the rects the compositor and the touch mapper use (every
frame, and whenever a window size is resolved). For the main window it calls
`Layout_Query(outputWidth, outputHeight)` first:

- `overridePlacements == false` (preset `32:9`): the DDGUltrawide arcade layout
  is kept, including the cabinet, perspective warp, and stock 2x2 sources
  (left top-left, center top-right, right bottom-left, touch bottom-right with
  822 visible rows).
- `overridePlacements == true` (`16:9` or single-screen): those rects replace
  the arcade cabinet. The first `activeCount` entries of `dest[]` / `source[]`
  are drawn (at most four). `dest` is a fraction of the output window; `source`
  is a fraction of the 3840x2160 frame. Screen index follows source order
  0 left, 1 center, 2 right, 3 touch. A single screen uses `focus` for that
  index so the touch panel still receives clicks. Pixel snap still applies.
  `GetCabinetScene`, `GetPerspective`, and the perspective touch-panel quad
  return false on this path, so the cabinet and the warp are not drawn.

The separate touch-panel window (`[TouchPanelWindow]`) still uses the upstream
placement path.
