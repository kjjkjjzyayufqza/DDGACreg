# Graphics quality — 2026-10-11

`features::Quality_Install` reads `[Quality]` from `config.ini` beside the DLL.
`Enabled=0` installs nothing. Otherwise it MinHooks console-variable writes and
pushes this executable's cinematic scalability, then keeps those values if a
later `Set` or a direct field write puts the low numbers back.

Image base `0x140000000`. RVAs below are added to
`GetModuleHandleW(L"TG4AC-Win64-Shipping.exe")`.

`sg=4` loads `@Cine`. Several arcade cuts are not in that section, and
`@Cine` itself sets `r.ViewDistanceScale=10`, so forcing 10 does not extend
the far clip past the cabinet's cinematic curve. The cull multiplies
`MaxDrawDistance` by the scale and does not clamp the top end.

## What the picture is actually running

`TG4AC\Config` has no `DefaultScalability.ini` and no
`DefaultDeviceProfiles.ini`. Scalability comes from
`Engine\Config\BaseScalability.ini`. Saved `Scalability.ini` and
`DeviceProfiles.ini` under `Binaries\Win64\..\UserData\Saved\Config\WindowsNoEditor`
are empty. The Windows device profile does not write quality cvars.

`sg.*` help text in the exe is `0:low, 1:med, 2:high, 3:epic, 4:cinematic`,
default 3. `sg.AntiAliasingQuality.NumLevels` defaults to 5. Group apply
(`sub_1414DA0C0` and its siblings) clamps the index to `NumLevels-1`. The last
index loads `Group@Cine` via `sub_1404DDD00`. Any lower index loads `Group@N`
via `sub_1404DDD70`. Cinematic is index 4, section `@Cine`, not `@4`.

`PerfIndexThresholds_*` only define transitions 0→1, 1→2, and 2→3. Autodetect
never selects cinematic. `DefaultGraphicsPerformance=Maximum` still leaves the
`sg.*` cvars at their C++ default of 3 (epic / `@3`).

`sg.ResolutionQuality` is not that index. Its callback (`sub_1414DA300` →
`sub_1414E5A10`) clamps the value to `[10, 100]` and writes
`r.ScreenPercentage`. Setting it to 4 would become 10% of the resolution.
`PerfIndexValues_ResolutionQuality` is `"50 71 87 100 100"`. The cvar itself
is the percentage. This hook writes `100`.

## Hook frame scale

`[Game] CenterWidth=2560` and `CenterHeight=1440` make the offscreen frame
5120×2880. The center quarter is 2560×1440. On a 1440p panel that is 1:1, not
an upscale. The compositor samples with a linear filter, which can soften by
a fraction of a pixel. It is not the low-detail source, and this task does
not change it.

`r.ScreenPercentage`, Left, Center, and Right are registered at 100. C++
default of `r.ScreenPercentage` is the float bits `1120403456` (100.0).
`r.ScreenPercentageTouchPanel=0` in `DefaultEngine.ini` stays 0 so the extra
touch view stays off.

`Engine\Config\Windows\WindowsEngine.ini` sets `r.setres=1280x720`. That name
is not a cvar in this exe. Saved `GameUserSettings.ini` is 1920×1080; the DLL
command line already overrides the window from `CenterWidth` / `CenterHeight`.
Neither is a quality-module change.

`dgo.AutoDestroyCachedMips=1` drops cached mips (help: `0 : not Drop / Not 0 :
Dropping now`). That softens textures independently of the scalability group.
Mip bias is already 0 at `@3` and `@Cine` (`r.Streaming.MipBias`,
`r.MipMapLODBias`). `r.MaxAnisotropy` tops out at 8 in this ini.

`@Cine` still sets `r.SkeletalMeshLODBias=0`. The -10 override is what clamps
skeletal meshes to LOD 0. There is no `r.ForceLOD` string in the exe.
`foliage.ForceLOD=0` is the foliage equivalent. Static meshes use
`r.StaticMeshLODDistanceScale=0.01` (higher values switch LOD earlier; 0 is
avoided so the scale is not a zero divisor).

`r.DistanceFieldShadowing=1` and `r.DistanceFieldAO=1` match `@Cine`, but
`DefaultEngine.ini` sets `r.GenerateMeshDistanceFields=False`, so those two
likely do not build distance fields. They are still written so a later group
apply cannot put the `@2`-and-below zeros back.

`r.DefaultFeature.Bloom=False` in `DefaultEngine.ini` is left alone.
`r.BloomQuality` is still pinned to the `@Cine` value 5.

## Arcade cuts `sg=4` does not undo

Names below are UTF-16 strings in `TG4AC-Win64-Shipping.exe`. The camera tick
already re-applies a drifted game-thread value. There is no second `Set` hook.

`r.ViewDistanceScale` is registered by `sub_1400AEAC0` (string `0x142411B28`,
C++ default `1.0`). The help text says the range is `[0, 1]`. The cache in
`sub_1415DE2E0` only does `fmaxf(value, 0)`. The distance cull in
`sub_140B64140` computes `scale * MaxDrawDistance` and does not clamp the
scale. The only code references of the name are that registration and the
cache read. Scalability ini apply goes through `Set`, which this hook
rewrites. `@Cine` writes `10`, the same number the previous force used, so
the far clip stayed on the cinematic curve. `100` is ten times that curve.
Foliage end-cull in `sub_1412F76B0` uses the same scale, then takes the
minimum against the screen-size distance.

## Left at the cabinet value

These were checked and not raised:

- Perspective far clip. The exe has `r.SetNearClipPlane` and `OrthoFarClipPlane`.
  There is no perspective far-clip cvar. `BaseEngine.ini` `NearClipPlane=10`
  is the near plane.
- A separate cull-distance cvar. `sub_140B64140` scales `MaxDrawDistance`.
  `r.Shadow.CSM.MaxDistance` and `r.Shadow.MaxCSMResolution` are not in the exe.
- `r.SkeletalMeshLODRadiusScale`. `sub_141561C80` clamps it to `[0.25, 1]`.
  The larger end keeps the higher LOD. The C++ default is the top of that
  range, and `r.SkeletalMeshLODBias=-10` already forces skeletal LOD 0.
- `r.DetailMode`. `@3` and `@Cine` are both `2`. The scalability cache clamps
  material quality to `0..2`.
- `r.ScreenPercentage` and the left/center/right splits. Already `100`.
  Resolution, window mode, and `CenterWidth` are unchanged.
- `foliage.DensityScale` and `grass.densityScale`. `@3` and `@Cine` are both
  `1`. The ini spelling `grass.DensityScale` is not the registered string.
- `r.MinScreenRadiusForLights` (`0.03`), `r.MinScreenRadiusForDepthPrepass`
  (`0.03`), and `r.MinScreenRadiusForCSMDepth` (`0.01`). They match
  `DefaultEngine.ini` and are not in a scalability section.
- `r.GenerateMeshDistanceFields=False` in `DefaultEngine.ini`. That is a
  startup flag. Forcing the distance-field cvars cannot build the fields.

## Where it sticks

Console manager singleton is `qword_142DD7F50` (RVA `0x2DD7F50`).
`FindConsoleObject` is `sub_140461EF0`. `IConsoleVariable::AsVariable`
(`vtable +40`) returns `this`, so the pointer from Find is the pointer `Set`
receives.

`Set` is vtable slot 11, three implementations:

| Target | RVA | Value at object +104 |
| --- | --- | --- |
| Int `Set` `sub_140472200` | `0x472200` | `int` |
| Float `Set` `sub_140472280` | `0x472280` | `float` |
| Int-ref `Set` `sub_1404723F0` | `0x4723F0` | `int*` |

The detour replaces the incoming string when `this` is one of the cvars in
the table, then calls the original. That covers blueprint and device-profile
`Set` calls. `ECVF_SetByConsole` (`0x0A000000`) is the highest priority in
this build (scalability uses `0x01000000`), so a rejected lower-priority
write leaves the previous value in place.

Scalability callbacks are installed once by `sub_1414D8450` (RVA `0x14D8450`),
behind `byte_142FEF114`. Applying a group index before that returns stores the
index and does not load `@Cine`. The detour calls the original first, then
forces the groups even if the stored index is already 4.

`APlayerCameraManager::UpdateCamera` (`sub_1414BD5B0`, RVA `0x14BD5B0`)
re-reads the game-thread value at +104 and writes again only when it drifted.
Direct stores that skip `Set` are caught there. `DoUpdateCamera` (RVA
`0x14A4D80`) is not hooked; the free-camera feature already owns that target.

If a read never matches after `Set`, that cvar is abandoned after three
attempts so a wrong offset cannot call `Set` every frame.
