# Coin input — 2026-10-11

Target: Densha de Go!! AC, TG4AC 5.80.02. IDA instance `ida-35608`.
Image base in the database: `0x140000000`. Runtime hook uses
`TG4AC-Win64-Shipping.exe` base + RVA.

`features::Coin_Install` reads `[Input] Coin` from `moduleDir + L"config.ini"`
(default `F3`) and, on a rising edge, inserts one local cabinet credit.
The online `addcredit` command is not used.

## Call that inserts the credit

`UKeyboardInput::CoinOperation` does not add a credit by itself. It latches
one edge. `UKeyboardInput::Update` is the function that turns a press+release
pair into one coin.

| Role | VA | RVA | Size |
| --- | --- | --- | --- |
| `UKeyboardInput::CoinOperation` | `sub_1401E6950` | `0x1E6950` | `0xE` |
| exec thunk `execCoinOperation` | `sub_1402E6A90` | `0x2E6A90` | `0x82` |
| `UKeyboardInput::Update` (hooked) | `sub_140209170` | `0x209170` | `0x470` |
| exec thunk `execUpdate` | `sub_14030AAF0` | `0x30AAF0` | `0x1A` |
| coin-switch state machine | `sub_140209940` | `0x209940` | `0x76` |
| multicast broadcast used by Update | `sub_1401A89A0` | `0x1A89A0` | `0x299` |

`CoinOperation` prologue `84 D2 74 05 83 49 28 01 C3 83 49 2C 01 C3`:

- `pressrelease != 0`: `or dword ptr [rcx+28h], 1`
- `pressrelease == 0`: `or dword ptr [rcx+2Ch], 1`

`Update` reads those same bytes first thing (`movzx` from `[rcx+28h]` and
`[rcx+2Ch]`, `lea rdx, [rcx+50h]`). Bit 0 is the coin switch. Neighboring
operations use other bits (`ServiceOperation` at `sub_140204890` uses bit 1,
`EnterOperation` at `sub_1401EA4A0` uses bit 3).

Reflected layout of `/Script/TG4AC.KeyboardInput` (UE4SS dump) matches the
offsets `Update` uses:

| Field | Offset | How Update uses it |
| --- | --- | --- |
| press latch (not a UProperty; first field after `UObject`) | `0x28` | bit 0 set by `CoinOperation(true)` |
| release latch | `0x2C` | bit 0 set by `CoinOperation(false)` |
| `DecreaseCoin` | `0x34` | subtracted after the optional increment, then cleared |
| `Coin` | `0x38` | incremented when the switch state becomes 3 |
| `CoinNumChangeDelegate` | `0x40` | broadcast `{Num, inc}` after `Coin` changes |
| `CoinSwitch` | `0x50` | byte state machine, signature of the change delegate is `KBCoinDelegate` |
| `CoinChangeDelegate` | `0x58` | broadcast when `CoinSwitch` changes |

`KBCoinDelegate__DelegateSignature` parameters are `Num` at offset 0 (`int32`)
and `inc` at offset 4 (`bool`). `Update` passes that pair in one stack slot
(`v23` / `v24`) to `sub_1401A89A0(this+0x40, &params)`.

### State machine (`sub_140209940`)

States observed in the byte at `CoinSwitch`: 0 idle, 1 down, 2 held, 3 pulse.

A press and a release latched in the same `Update` call, starting from 0,
writes state 3 and returns "changed". `Update` then does `Coin = Coin + 1`
only when the byte equals 3, broadcasts `CoinNumChangeDelegate` with
`inc = true`, and clears both latch dwords (`mov qword ptr [this+28h], 0`).
The next `Update` with empty latches moves state 3 back to 0 and does not
increment. So one press+release pair is one credit, and a second pair must
wait until the switch is idle again (one game tick later).

The hook is `Update`, not `CoinOperation`. The detour runs on the game thread,
and only when `CoinSwitch == 0` it calls `CoinOperation(this, 1)` then
`CoinOperation(this, 0)` before the original body. That is the same pair the
exec thunk produces. The original `Update` performs the increment. The poll
thread never writes the object and never injects input into another process.
`GetAsyncKeyState` only samples the configured virtual key. MinHook is
initialized with `MH_ERROR_ALREADY_INITIALIZED` ignored, and only this
`Update` target is enabled.

`execUpdate` does not call `Update` with an explicit register move. At
`0x14030AB05` it tail-jumps (`E9`) and `rcx` is still the `UKeyboardInput`
instance. The only code reference to `sub_140209170` is that jump. The data
reference at `0x14334D874` is `.pdata` (`BeginAddress` RVA `0x00209170`),
not a second caller.

## Why this path, not `addcredit`

`addcredit` is the online NESiS command stub `sub_140221E20` (ASCII at
`0x14239AD40`), already recorded in `2026-10-11-research.md`. This session
did not call it. A local F3 press has to hit the cabinet coin latch, which
is `CoinOperation` plus `Update`.

`UMarshallingIO::Update` (`sub_1402467A0`, exec thunk `sub_14030AB10`) is the
cabinet IO poll. Its native table is `sub_14027C530` (`EnabledWDT`,
`GetDeviceState`, `Update`, and the NESiCA calls). It has no `CoinOperation`.
The shared switch helper `sub_140209940` is referenced only from
`KeyboardInput::Update`. The keyboard coin button is the local path that
matches an F3 edge.

## Config and hook behavior

- INI: `[Input] Coin`, `GetPrivateProfileStringW`, default `F3`.
- Names: `F1`–`F12`, `A`–`Z`, `0`–`9`, `SPACE`, `SHIFT` (`VK_SHIFT`),
  `CTRL` (`VK_CONTROL`), `UP`, `DOWN`, `LEFT`, `RIGHT`, and `0xNN` (one or
  two hex digits). Anything else falls back to `F3`.
- Rising edge is sampled on a thread with `GetAsyncKeyState` every 5 ms.
  The key already being down when the thread starts does not insert a credit.
- Each rising edge queues one credit. `Update` consumes one queue entry per
  call, and only while `CoinSwitch == 0`, so two edges closer than two ticks
  stay queued instead of collapsing into one latch.
- Prologues are checked before the hook (`48 89 5C 24 10` at Update,
  `84 D2 74 05 83 49 28 01 C3` at CoinOperation). A mismatch leaves the
  process unhooked.
- `MH_EnableHook` is called with the Update address only.

## What this session could not prove

- The game was not launched. The one-credit result is the state machine in
  `sub_140209170` / `sub_140209940`, not a live credit counter.
- No native caller of `CoinOperation` or `Update` exists besides the exec
  thunks. Something still has to `ProcessEvent` `KeyboardInput::Update` each
  tick (blueprint or a reflection lookup). That caller has no direct xref.
  If no live `UKeyboardInput` is updated, the hook never runs and F3 does
  nothing.
- How many `UKeyboardInput` instances tick. The detour will pulse every
  instance whose `CoinSwitch` is 0, but a compare-exchange takes only one
  queued credit per call.
- The blueprint wire from `KeyboardInput.CoinNumChangeDelegate` to
  `CreditsManager.CoinNumChangeDelgate` (the blueprint spells it `Delgate`).
  `CreditsManager`, `GetInsertedCoin`, and `InsertServiceCoin` are not ASCII
  or UTF-16 strings in this image. `UCreditsManager` in the Lua dump is a
  blueprint class (`CreditsManager_C`), so the bind lives in cooked
  blueprint bytecode, not in a native function this session could hook.
- Whether a cabinet with a live `UMarshallingIO` ignores the keyboard coin
  delegate and only credits the IO object's `Coin` at offset `0xB8`. The IO
  `Update` was identified and not hooked, because it is the device poll and
  it does not share `sub_140209940`.
- `sub_1401A89A0` was not fully proven to be `FMulticastScriptDelegate::Broadcast`
  beyond its use: `Update` calls it with the delegate address and the
  `{Num, inc}` pair, and the body walks an invocation list and calls through
  a virtual at offset 464. That is enough to treat it as the broadcast, not
  enough to name the engine symbol.
